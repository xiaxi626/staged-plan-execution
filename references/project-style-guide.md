# 项目风格要求（所有步骤通用）

> 此段内容在生成的 prompt 中作为"## 项目风格要求（所有步骤通用）"小节输出，且在交接 prompt 中作为"逐字复制段落"之一原样复制。

## DeepSeek harness 插件生态识别

当前项目属于 DeepSeek harness 插件生态，典型特征：

- 中英双语 CONTRIBUTING（`CONTRIBUTING.md` + `CONTRIBUTING.zh-CN.md`）
- `src/` 源码、`test/` 测试、`lib/` tsc 编译产物三段结构
- 测试文件命名 `xxx.test.ts`，使用 `node:test` + `tsx`
- CLI 命令前缀 `dsh-`
- CHANGELOG 采用 Keep a Changelog 风格，极其详细

## 先阅读以下文件

在动手之前，你必须先阅读以下文件以理解当前项目的一贯风格：

- `CONTRIBUTING.md` 和 `CONTRIBUTING.zh-CN.md`——项目结构、质量门禁、提交规范
- **与本方案涉及文件相邻或同类功能的源文件**——注释风格的范例：每个函数、每个设计决策都有解释"为什么"的 JSDoc / TSDoc
- **与本方案涉及文件同名的测试文件**（如方案改 `src/foo.ts` → 读 `test/foo.test.ts`）——测试风格的范例
- `CHANGELOG.md`——CHANGELOG 风格的范例：极其详细，包含背景、变更、验证方式、"不做"的决策及理由

> **生成 prompt 时**：agent 应扫描 plan 中提到的具体源文件路径，在上述第二条和第三条中点名具体文件名，而非保留泛化表述。

## 关键风格约束

1. **注释密度**：每个导出函数必须有文档注释，解释设计决策和边界条件，不是复述代码在做什么
2. **测试**：使用当前项目采用的测试框架和运行方式，参考现有测试文件的模式。每个测试文件用临时目录隔离环境，使用当前项目测试框架的清理钩子（如 `after()` / `afterEach()` / `teardown`）
3. **质量门禁**：每完成一个步骤后，必须运行当前项目的质量门禁命令（如 `{{typecheck_cmd}}`、`{{lint_cmd}}`、`{{test_cmd}}`）确认全部通过，然后再进入下一个步骤
4. **不要修改编译产物目录**（如 `lib/`、`dist/`）——它是编译产物，在每个步骤完成后统一重建
5. **CLI 和 HTTP 路由（或同等入口）共享 core 层函数**——改动放在 core 层，不要分别在各入口里重复实现
6. **参数解析**：参考当前项目现有命令的 argv 解析风格（如是否接受 `--flag=x` 内联值、如何处理未知选项和位置参数），保持一致
